## 7. The candidate features, one by one

Ratings use the scale of section 1.1 (3 native, 2 with a script or helper, 1 awkward, 0 cannot). "s6+layer" means s6 with s6-rc plus the one policy program of section 1.4. Value, cost and risk are my reading (BELIEVED) unless a test is named. Nothing in this table was built except where the "evidence" column names a test.

| # | Feature | Value to the hub | Cost to build | Risk | s6 alone | s6 + layer | Evidence |
|---|---|---|---|---|---|---|---|
| F1 | Boot progress screen on the projector, plain words, errors in words | Medium: the owner is not an operator, and a black projector during a 20 s boot or a failed boot is unreadable | Small if it is only lines written to the kernel's text console (the console shows on the projector until driftwm takes the screen); a nicer screen means a drawing program | The text console and driftwm both want the display; the hand-over is UNKNOWN (needs a real GPU) | 2 (a stage-1 script can print) | 2 (the layer prints per-service words, translated from the dependency graph) | none; not tested |
| F2 | Boot timeline history, regressions flagged | Medium: finds a slow change before the owner feels it | Small: record "service, started, ready" per boot (s6 reports `ready N seconds`), keep the last N boots, compare to the median | A timing threshold needs real hardware numbers (QEMU timings are not usable) | 1 | 2 | the data source exists: `s6-svstat` prints "up (pid) S seconds, ready R seconds" (TESTED, appears in the logs) |
| F3 | Boot self-tests (disk, GPU, network, time) into the crash record | High for support: the first thing the owner wants after a bad boot is "what was wrong" | Small per test; s6-rc one-shots with dependencies are the natural form | A self-test that hangs must not hold up the boot (needs a timeout) | 2 (s6-rc oneshot services) | 3 | s6-rc oneshots: source documentation (read 2026-10-05, `s6-rc-0.7.0.0/doc/`); not run here |
| F4 | Safe boot: if a new config fails validation, boot the last good config and alert | High (this is the update/recovery story for config-only changes) | Medium: two config generations on the config partition plus a validator; the choice of database is a stage-1 decision | The validator itself must be simple (a bug there would reject good configs) | 2: s6-rc keeps compiled databases as directories and `s6-rc-init -c DIR` chooses one; `s6-rc-update` switches live | 3 | graph validation at build time: TESTED (section 5.5); choosing a database: SOURCE `s6-rc-init` documentation |
| F5 | Config validated at build time and at boot | High | Build-time graph check exists for s6-rc and dinit (TESTED); the machine config to graph generator is ours either way | Low | 3 for the graph, 0 for the inventory (hubd's own validator does that) | 3 | TESTED: broken graphs rejected by `s6-rc-compile` and `dinit-check` |
| F6 | Credentials handed to services without command lines | High (hub-user-split.md); keeps secrets out of `ps` | Small | Environment variables are still readable by the same user and root in `/proc/PID/environ` | 3: execline `redirfd -r 3 FILE` opens a root-only file on fd 3 before the program starts | 3 | TESTED: argv and environ contained no secret, fd 3 delivered it; `s6-envdir` put it into the environment (visible). dinit has `env-file` (environment only) and no fd passing (SOURCE: dinit-service(5), read 2026-10-05) |
| F7 | Built-in timers for housekeeping (NAS backup, log capping, time sync) | Medium: replaces cron and an extra daemon | Small: a monotonic-clock loop in the layer | A timer on the wall clock misfires after a clock jump (TESTED jumps do not disturb s6 or the brains) | 0 (s6 has no timer; busybox `crond` would be another daemon) | 2 | none of s6, runit, dinit, OpenRC has timers (SOURCE: their manuals, read 2026-10-05); systemd has timers (named for ideas only) |
| F8 | Per-service resource limits and priorities | High for driftwm and hubd | Small | cgroup v2 controllers must be enabled by stage 1 | 2 (script: `echo > cgroup.procs`, `nice`, oom score) | 2 | TESTED: the POLICY lines in section 5.1; dinit declares it natively (`oom-score-adj`, `nice`, `run-in-cgroup`); OpenRC's `supervise-daemon` has `--nicelevel` and `--oom-score-adj` (SOURCE: man page) |
| F9 | Structured, capped log queryable by hubd | High: the recovery agent serves `/v1/logs` | Small | A full disk must not stall the services (TESTED, section 5.2) | 2 (`s6-log` caps and rotates, files are plain text) | 3 (layer adds a query on the status socket and the crash record) | TESTED: s6-log kept the services running with the log disk full |
| F10 | A diagnose command that gathers the facts for any service | High for support | Small in the layer: state, last exit status, last log lines, probe result, dependencies, recent crash records | None | 1 | 3 | the pieces exist as separate commands in each candidate; the crash records and the status line were produced by the prototypes (TESTED) |
| F11 | Live service-graph view through the status socket | Medium | Small | None | 2 (`s6-rc-db`, `s6-rc -a list`) | 3 | TESTED: the prototype's status socket lists state, `needs`, restart count and last failure per service |
| F12 | Orderly stop sequence for restarts the owner chooses | Medium: avoids killing a game or a long job by surprise | Small: `s6-rc -d change` stops in reverse dependency order with timeouts | A restart must still refuse while a game runs (that is the node helper's rule) | 3 | 3 | SOURCE: s6-rc documentation; not run |
