# watcher: TEST STAND-IN. NOT the product watcher. The hang rule is not built.

A small Go program (`go build -trimpath -ldflags="-s -w"`, static) used only by the init comparison (`docs/proposals/init-comparison-run.md`, follow-up 4) to measure what an init does for a hung compositor once a separate watcher exists. It is **not** the product watcher and decides nothing about where the product's hang rule lives.

**Probes, limits, latch and identity rule (one line, follow-up 5, latch version):** it probes the compositor twice per round, with driftwm's socket `state` request (5 s deadline) and with a Wayland `wl_display.sync` round trip (2 s limit), and applies the owner's rule of `docs/proposals/hub-stability.md` section 9.1 (a round fails only when BOTH probes fail; kill after 4 failed rounds in a row and at least 30 s since the first failed round; at most 3 kills in 10 minutes; never reboot anything); when the rule wants a 4th kill it LATCHES and stays stopped until a person clears it; it kills only the same process (id AND start time) that was failing at the first failed round of the streak.

**Other things it does.**
- The hubd `ping` is still sent every round and is written in the log as `hubd(info only)`; it takes no part in the decision.
- It restarts nothing: the init restarts what it killed. It has no restart ladder, no alert and no conductor.
- `Probe` (the `state` request) is copied unchanged from `../go/probe.go`; `ProbeSync` speaks the Wayland wire format by hand (see its comment).

**Kill budget in a file (owner decision 4).** The times of the kills made in the last 10 minutes are kept in `/run/hubos/watcher.budget` (`/run` is the in-memory area), so a restarted watcher does not get a fresh budget. Every kill is written at once, by writing a temporary file next to it and renaming it over the real one. Clock: `CLOCK_BOOTTIME` (time since the kernel started): it is not changed when someone sets the wall clock (the fault suite sets it back an hour and forward a day), it can be read again by a new process, and it restarts from zero only at a reboot, which also empties `/run`, so file and clock always belong to the same boot. On start the watcher reads the file; if it is missing or damaged (bad header, a line that is not a time, a time in the future, wrong count, text after the end line) it starts with an empty budget and logs that it did. The 30-second streak is NOT kept: a restarted watcher starts counting the 30 s again.

**Latch (follow-up 5, decision 1; `latch.go`, `watcher.go`).** When the cap is reached and the rule wants a 4th kill, the watcher writes the latch file `/run/hubos/watcher.latch` (temporary file, flush, rename) and stops killing; it stays stopped, however much time passes, until a person clears it. The latch is read at start and in every round, so it survives a watcher restart. A latch file that is there but damaged counts as latched (the safe side) and is logged; it never crashes the watcher. **Person-command, test hook only:** `watcher reset` (same binary) empties the budget file (first), removes the latch and removes the state file; a running watcher notices within one round. This is only the hook for the test; **the product's command is not designed.** The measured behaviour of the follow-up 4 version (killed again about 485 to 492 s after the cap) is the "window" version; `Rule.Round` and its tests keep it.

**Identity rule (decision 3).** At the first failed round of a streak the watcher records the compositor process: id AND start time (field 22 of `/proc/PID/stat`, so a reused id is not taken for the same process). At the kill moment it kills only if that identical process is still there. If it is gone or another one (the init already restarted it) it logs `SKIP: process changed`, does not kill, counts nothing, and starts a new streak with the new process (its own 30 s). A kill that finds no process is never counted (the budget entry is taken back). If several processes carry the name, the first (lowest id) is the recorded one.

**Probe limits (decision 4).** `state` 5 s, `wl_display.sync` 2 s (the follow-up 4 watcher used 1 s for both). The hubd ping (information only) keeps 1 s. A round with slow probes therefore lasts up to 5 s.

**State file (owner decisions 3 and 2).** Now: `capped <UTC time>` is written when the rule wants a kill and the latch (or a full budget) blocks it; it is removed in the first round in which BOTH probes answer, and by `reset`; the latch itself stays. Original text of follow-up 4, kept for the record:  When the cap blocks a kill, the watcher writes one line `capped <UTC time>` to `/run/hubos/watcher.state`, and removes the file in the first round in which the budget has room again (kills are allowed). This is only the hook a bar would read; there is no bar or panel here.

`go test ./tools/bench/init/prototypes/watcher/` (10 tests of follow-up 4, 12 new ones of follow-up 5: latch set at the 4th wanted kill, no kill while latched after more than 10 minutes, latch survives a restart, reset, state file coming and going, identity rule (same id and start time kills; same id with another start time, another id, none: no kill, nothing counted, new streak), crash storm kills nothing, streak not kept over a restart, damaged latch, probe limits (state after 4 s answered, sync after 3 s failed; takes 9 s), slow but alive never kills) tests the rule (4 rounds and 30 s, both probes must fail and one failing is not enough, an answer resets the streak, 3 kills in 10 minutes and the budget coming back), the budget file (survives a restart, a damaged file does not crash it, entries older than 10 minutes drop out), the state file, and the sync probe against a fake server.

`-wd3` candidates (`s6rc-par-wd3`, `runit-111-wd3`) carry this version; `-wd2` carry the window version (their build.sh copies whatever watcher binary is built from this folder, so to rebuild `-wd2` the folder must be taken from commit f130829; the -wd2 images were not rebuilt and their rows are unchanged).

The program of follow-up 3 (rule "compositor and hubd probes", and the `-mode compositor` variation) is kept unchanged in `../watcher-fu3/`; the rows `s6rc-par-wd`, `runit-wd`, `s6rc-par-wdc`, `runit-wdc` were measured with it.
