## 0. Plain-words summary

1. **What a machine needs, in one paragraph.** The cluster's update and recovery plumbing is a handful of fixed pieces, and almost none of it cares which Linux distribution is on the machine: a disk with five named partitions; an update bundle (a signed list of hashes, two kernels and a root image); one kernel per slot with a tiny "stage 0" program built into it; a "confirm" step that says "this boot was good"; a watchdog feeder that keeps the machine from being reset; a counter in the firmware's memory that sends a machine with a broken system to the recovery kernel; the recovery kernel itself; and, on the network, one small API on port 8480 plus the remote-screen server. Section 1 lists these one by one.
2. **What is only our reference build.** Ubuntu 24.04, the `mmdebstrap` snapshot build, s6, the little shell script that is PID 1, the busybox tools, and (on the hub) driftwm, eudev and Waybar. A node distro does not need any of them if it provides the same behaviour.
3. **The good news.** The slot kernels, stage 0, the failure counter, the recovery kernel and the update tool `hubos-ctl` are built by this repository's tools and do not use the distro at all. A distro's job is smaller than it looks: provide a read-only root image that contains certain files and tools, and run two services after boot (confirm, then the watchdog feeder).
4. **The not-so-good news (found by reading the code).** (a) The update tool `hubos-ctl` is a shell script that expects BusyBox-style tools (`watchdog`, `udhcpc`, `wget`, `stat`, ...) and the real `findfs`, `chattr`, `efibootmgr` and `signify-openbsd`; a distro must carry them. (b) The recovery kernel is assembled from the **glibc** root of the reference build (`tools/image/recovery-list.py` hard-codes `x86_64-linux-gnu` library paths and `ld-linux-x86-64.so.2`); for a musl distro it would have to be built from the reference root anyway or changed. (c) `hubos-ctl` hard-codes the disk `/dev/vda` and partition 1 when it creates boot entries, which is wrong for a real NVMe machine. (d) Stage 0 hands the three timeout settings to the init as **environment variables**; whether systemd passes those on to its services is UNKNOWN, so a systemd node should re-read the config file. (e) Nothing defines what "this boot was good" means on a node other than the hub (the only definition in the repository is "hubd answers five times").
5. **Does the contract work under systemd? (EXPERIMENTS ONLY after the owner's correction of 2026-10-05: no cluster machine runs systemd.)** Mostly yes, as plain shell scripts started from units (confirm as a oneshot unit, the feeder as a service). The two real differences are in section 1.3: systemd can also feed the watchdog itself from the first second of boot, which is **not** the same behaviour as ours (ours feeds only after a confirmed healthy boot), and the `s6-svc` lines in the confirm script have no meaning there. All of this is BELIEVED; none of it was run.
6. **Candidate bases (section 2).** (Owner correction 2026-10-05: only non-systemd bases are candidates; see the Owner decisions section above. The systemd-only rows below are kept as research and are experiments only.) For a node that needs glibc (gaming box, AI box if NVIDIA needs it) the realistic choices are Debian, Ubuntu, Fedora, Arch, openSUSE, Gentoo, NixOS and Void-glibc. For nodes that do not need glibc (a pure NAS, a small appliance) Alpine, Void-musl and Chimera are also possible, and Alpine matches the repository's tools best (BusyBox native). Only Debian, Ubuntu and Arch give a dated archive of their packages out of the box (SOURCE below); only Yocto and Nix claim strong build reproducibility by design. The support periods differ a lot: Debian 5 years, Ubuntu LTS 5 years (10 with a paid add-on), Alpine about 2 years, Fedora about 13 months, NixOS about 7 months (third party), Arch none (rolling).
7. **From scratch (section 3).** The repository already gives a new distro the whole boot, update, rollback and recovery machinery plus a QEMU test runner. It must still add a libc and toolchain, a package build system, an init and service manager, the userland tools, the kernel drivers and firmware per machine, the graphics/audio/display stack, and a way to track security fixes. That last item is the real cost.
8. **Conformance test (section 4).** Twelve checks, run in QEMU against a candidate root image. Most of them already exist in `tools/image/qemu_test.go` for the reference root; the work is to make the root image a parameter.
9. **Questions for the owner:** section 5. The biggest ones: may a node use its distro's own kernel (then stage 0 cannot be built into it), who defines "healthy" on a node, and how many distro families do you want to maintain.

## 1. The contract

### 1.1 How to read the table

Each row is one thing the update and recovery plumbing needs from a machine. Columns:

- **Item and exact names.**
- **Kind.** **CONTRACT** = a distro must provide it exactly (names, formats, behaviour), because code in this repository reads or writes it. **REF** = only our reference implementation; any distro may do it differently if the contract rows above it still hold.
- **Depends on today** (SOURCE, the repository): `s6`, `busybox`, `Ubuntu` (the Ubuntu 24.04 root or glibc/Debian paths), `no-systemd` (a rule or a test), or `none`.
- **Unchanged under systemd? (experiments only)** Would the same file or command work if the distro's init were systemd? Everything in this column is **BELIEVED** unless it says otherwise: no node distro with systemd was built or run, and I did not run systemd.

Where a row says "ours" it means the piece is built or provided by this repository's tools, not by the distro.

### 2.5 Two systemd facts that affect the contract (EXPERIMENTS ONLY: no cluster machine runs systemd)

1. **Boot counting exists in systemd-boot.** systemd documents "Automatic Boot Assessment": the boot loader entry file name carries a counter (`+3` becomes `+2-1` and so on), `systemd-bless-boot.service` marks a boot good after `boot-complete.target`, and `systemd-boot-check-no-failures.service` can make "no failed services" a condition (page read). It needs `systemd-boot` as the boot loader. Our design deliberately has **no bootloader** and its own counter in EFI variables (C1, C10). A systemd node could use either; they should not run together. This is a design choice (Q6), not a finding that one is better.
2. **systemd's own watchdog use** is described under C9. Default off; if on, systemd feeds from PID 1 start.

### 3.2 What a from-scratch distro must add (BELIEVED unless a repository file is named)

1. **A libc, toolchain and the set of base packages**, or an existing build framework to supply them (Yocto, Buildroot, Chimera's tooling). `HUB-OS.md` earlier said glibc everywhere; the owner's decision allows musl on nodes that do not need glibc (systemd is not allowed on any cluster machine). The gaming box needs glibc (Steam/Proton, SOURCE `HUB-OS.md`); whether NVIDIA's driver does is **UNKNOWN** (it is on the unverified list).
2. **A way to describe, build and pin every package** (a recipe format, a build farm or at least a repeatable build script per package) and a place that stores the built packages. Today the repo avoids this by using Ubuntu's archive at a dated snapshot.
3. **A way to learn about security fixes** in every package it ships and to rebuild and release. This is the standing cost of owning a distro: the table in 2.2 shows what the others spend people on (Debian 5 years, Ubuntu 5 to 10, Alpine about 2). For a cluster with at most 20 machines the burden is "how many packages", which depends on the roles; not measured.
4. **An init and service manager** and the service directories for each role. The repository has s6 plus plain shell scripts and says the init is "kept swappable" (SOURCE `HUB-OS.md`); the missing init-neutral service up/down command (C13) would be part of this.
5. **Userland tools** listed under C5, in particular a `watchdog` feeder, a DHCP client, `wget`, `efibootmgr`, a `signify`, `findfs` with `PARTLABEL=`, `chattr`. Today BusyBox and Ubuntu packages provide them.
6. **Kernel configuration per machine**: the fragments in `image/kernel/` cover QEMU and the hub's virtual devices only. Real AMD boards need real disk, network, GPU, watchdog drivers and firmware blobs; the first-boot driver set for real hardware is **UNKNOWN** until December. The watchdog driver for the real boards is not chosen (the tests use QEMU's `i6300esb`).
7. **The graphics, audio and display stack** on nodes: Wayland compositor (wlroots-based), wayvnc and neatvnc built at pinned tags, PipeWire, dbus, Mesa and the GPU driver stack (and CUDA or ROCm for the AI box). None of it is in an image yet except the hub's.
8. **Out-of-tree kernel modules** (NVIDIA, OpenZFS) built with the machine's kernel: declared in HUB-OS.md, listed in the manifest, no code yet (SOURCE `docs/image.md` 3.1).
9. **The node helper** (C13) and the init-neutral service command.
10. **A policy for libc compatibility**: a musl base cannot run glibc-only programs (Steam, probably NVIDIA's userspace). Alpine's wiki has a page "Running glibc programs" (title read; contents not read).

### 3.3 Where the line falls

Using an existing distro costs the owner its choices (init, kernel packaging, update cadence). Building from scratch costs the items above. A middle way, which I describe and do not recommend, is to use a build framework (Yocto or Buildroot) as the "from scratch" tool: Yocto's manual claims 100 percent reproducible recipes with named exceptions (section 2.2) and lets the image choose its init and libc. Whether either fits the AI or gaming box's GPU stack is **UNKNOWN**.

## 4. A conformance test (sketch, not built)

**Goal:** a candidate root image passes if the cluster's plumbing works with it. **How:** reuse `tools/image/qemu_test.go`: it already builds a disk with OVMF variables, serves bundles from the host, drives the serial console, retries QEMU hangs and crashes, and makes throwaway keys. The change needed is to let the test take the **root image (squashfs)** and the **machine file** as inputs instead of building the Ubuntu root itself. The kernels (slot a, b, recovery) are built by our tools as today.

## 5. Questions for the owner (batched)

**Kernel and boot**
- **Q1.** May a node use its **distro's own kernel package**? Today stage 0 and the per-slot command line are **built into** a kernel we compile from kernel.org (C6). A distro kernel cannot have that. The alternatives are: (a) every node uses our kernel build, the distro only supplies userland, modules and firmware; (b) a unified kernel image made from the distro's kernel plus our stage 0 as its initramfs plus the command line (BELIEVED possible with `ukify`, whose manual page I fetched but did not read in full; not tried); (c) different rules per node. Which?
- **Q2.** `hubos-ctl` assumes the disk is `/dev/vda` and partition 1 is the boot partition when it creates boot entries (C1). Real machines are NVMe or SATA. Should the contract take the disk from `node.conf` (a new key), from the partition label, or from the boot partition's mount, or do you want me to propose it?
- **Q3.** The watchdog driver of the real boards is unknown until December. Until then conformance tests use QEMU's `i6300esb`. OK?

**Health and the confirm step**
- **Q4.** What does "this boot was good" mean on a node that is not the hub? The only definition in the repository is "`hubd` answers five times in a row" (hub only). Candidates: the node helper answers `GET /v1/live`; the display server's port accepts a connection (that is the existing "ready" definition in `HUB-OS.md`); both; or the role's own check.
- **Q5.** (Experiments only.) Who feeds the watchdog on a systemd node? (a) Our feeder, started after the confirm step, as now (an unhealthy boot is reset or rolled back; the feeder never runs for a bad boot); (b) systemd's `RuntimeWatchdogSec=` (feeds from early boot; a hung service is no longer caught by the watchdog, only by the confirm timeout). The contract should state one.
- **Q6.** (Experiments only.) On systemd nodes, keep our EFI-variable failure counter and no bootloader (as now), or allow systemd-boot's boot counting? They must not both run (section 2.5).

**What a distro must carry**
- **Q7.** The recovery kernel is built from the **reference glibc root** today (C11). For a node whose own root is musl or has another library layout, should the recovery kernel still be built from the reference (Ubuntu) root? (That keeps one recovery kernel for all machines; it is a decision about where the recovery tools come from.)
- **Q8.** Is it acceptable that **every** node root carries BusyBox (or equivalents of its `watchdog`, `udhcpc`, `wget` applets) and the shell script `hubos-ctl` unchanged? The alternative is to rewrite `hubos-ctl` in Go (the hub's language is Go; I see no rule that forbids it, but it would be a rewrite of a tested 290-line script and I did not weigh it).
- **Q9.** Distros that bring their own rollback (NixOS generations, openSUSE MicroOS snapshots, Fedora CoreOS rpm-ostree) overlap with our A/B. May a node use such a distro **only if** its own rollback is switched off or unused? Or are they excluded?
- **Q10.** `node.conf` is read by stage 0 and `hubos-ctl` with `sed` but **sourced** (`.`) by the reference stage-1 script. For a systemd node, is "key=value parsed by a small reader, never sourced" acceptable as the contract? (This also affects secrets hygiene.)

**Choosing distros**
- **Q11.** How many distro families do you want to **maintain** at once? Every family adds a root builder, an update cadence to follow, and a conformance run. My reading of the support lengths (section 2.2) is that Debian, Ubuntu LTS and Alpine give the longest fixed windows; Arch, Gentoo, Void and Chimera are rolling; Fedora and NixOS have the shortest fixed windows.
- **Q12.** How long must a node run **without a distro version change**, and do you accept a node on a rolling distro (Arch, Void, Gentoo, Chimera), where "pin to a date" is the only way to get repeatable builds and only some give a dated archive (Debian, Ubuntu, Arch confirmed above; others UNKNOWN)?
- **Q13.** Which roles must be glibc (gaming box: yes, per HUB-OS.md; AI box with NVIDIA: **UNKNOWN**), and which may be musl (NAS? VM host?). This decides whether Alpine, Void-musl or Chimera are even candidates.
- **Q14.** (Moot after the owner's correction.) Should a systemd node's root be **allowed to contain** systemd programs in an image that the hub's tests (the "no systemd program" tests) would reject? Those tests are written for the hub today (SOURCE `docs/image.md` section 4). I assume they stay hub-only; please confirm.

**Conformance test**
- **Q15.** Do you want the conformance test as a parametrised version of the existing Go test (my sketch), or as a separate command that takes a root image and prints a pass/fail list the owner can read?
- **Q16.** The reference health check for the test needs a stand-in on nodes (a fake helper). Is a small test-only program acceptable, like `tools/fakenode`?
