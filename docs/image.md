## 2. How to build and run

Needs: Linux, root (QEMU runs without KVM; `mmdebstrap` runs in `--mode=root`), Go, `gcc`, `make`, `flex` and friends are unpacked by the first script. **Nothing is installed**: `fetch-tools.sh` downloads the packages and unpacks them into `$WORK/tools/root` with `dpkg -x`. Disk: about 5 GB in `$WORK`.

```
# the normal tests (do NOT run the image build):
go test -count=1 ./...

# the image tests (build tag "qemu"); everything below happens inside one temporary directory:
go test -tags qemu -count=1 -timeout 150m -v ./tools/image

# THE QEMU TESTS ARE RUN BY HAND before merging any change to image/ or tools/image/ (they are not part of
# `go test ./...`, they take 12 to 20 minutes, and they need root).

# keep the long build between runs (the kernel and the root are rebuilt only when their inputs change):
HUBOS_IMAGE_WORK=/tmp/hubos-image go test -tags qemu -count=1 -timeout 150m -v ./tools/image
```

The scripts can also be run by hand (`WORK=/tmp/x tools/image/fetch-tools.sh`, then `build-kernel.sh`, `build-base.sh`, `build-bundle.sh 2 good DIR PUBKEY SECKEY`, `build-disk.sh ROOT KERNEL DIR`). `MACHINE=image/machines/other.build` selects another machine file.

**How the image is built:**
1. `build-kernel.sh`: downloads `linux-$KERNEL_VERSION`, `make tinyconfig`, appends the machine's fragment (with the stage 0 list and slot `a` filled in), builds the `bzImage` as `kernel-a.efi`; then changes only the slot name in the built-in command line (`hubos-root-a hubos.slot=a` to `hubos-root-b hubos.slot=b`) and builds again as `kernel-b.efi`; then swaps the initramfs for the **recovery** one (`recovery-list.py`: busybox, `hubos-ctl`, `efibootmgr`, `signify`, the owner's **public update key** (`UPDATE_PUB`, a file the caller passes; it is not in the repo), e2fsprogs with `chattr`, `findfs`/`blkid`, the network script and the libraries they need, copied from the base root and the unpacked tools) and the command line for one without `root=` and builds `kernel-recovery.efi`. The slot kernels and the recovery kernel have separate stamps, so a new key rebuilds only the recovery kernel (about a minute); the later builds recompile only what depends on the changed parts. The base root is built first if it is not there. The build refuses a machine file whose timeouts break the rule of section 3.10. `KBUILD_BUILD_TIMESTAMP`, user and host are fixed so that two builds can be compared.
2. `build-base.sh`: `mmdebstrap --mode=root --variant=minbase --components=main,universe noble` with the machine's package list, from **`http://snapshot.ubuntu.com/ubuntu/$SNAPSHOT`** (a dated snapshot of the archive), with `SOURCE_DATE_EPOCH` set and, through a setup hook, `image/apt/no-systemd.pref` placed in `/etc/apt/preferences.d/` before the first package is installed. Output: a tar file.
3. `build-root-image.sh`: unpacks the base, copies `image/rootfs`, the static `hubd` (`CGO_ENABLED=0 go build -trimpath`), `efibootmgr` and `signify`, the public key, writes `/etc/hubos-release`, **removes** the unit files and rules packages ship for systemd and udev (`/etc/systemd`, `/usr/lib/systemd`, `/var/lib/systemd`, `/usr/lib/udev`: inert, from `e2fsprogs`, `util-linux`, `dpkg`), then **strips** the root (`strip-root.sh`: the files of `apt`, `libapt-pkg6.0t64`, `procps`, `libproc2-0`, `libpam-runtime`, `libpam-modules`, `libpam-modules-bin`, `login` and `passwd`, taken from dpkg's own file lists; busybox supplies `ps` and `pidof`), runs `check-libs.sh` (**the build fails** if `ldd`, run inside the root, finds an unresolved library in any ELF file under `/usr`, `/bin`, `/sbin` or `/lib`), and packs a squashfs (zstd; `SOURCE_DATE_EPOCH` fixes every time stamp). Bad flavors for the tests: `noinit`, `garbage`, `unhealthy`, `hang`.
4. `build-bundle.sh`: root image + the **two slot kernels** (`kernel-a.efi`, `kernel-b.efi`) + a manifest (`version`, `flavor`, `arch`, **`kernel-version`**, **`modules`**, **`recovery-version`**, sha256 and size of the root and of the slot kernels, and the sha256 and size of the **recovery kernel that is inside the root**) signed with `signify`. The bundle carries no separate recovery file: `build-root-image.sh` puts `kernel-recovery.efi` and `recovery.version` into the root under `/usr/lib/hubos/recovery/` (section 3.7).
5. `build-disk.sh`: a 420 MiB GPT disk (boot, slot A, slot B, config, data), partitions made as separate files and put in place with `dd` (no loop devices), plus a writable copy of OVMF's variable store. The boot partition gets `kernel-a.efi`, the recovery kernel (`kernel-recovery.efi`, with `recovery.version`) and the fallback loader. The node config (`/config/hubos/node.conf`) gets the three settings, after the same timeout check.

### 3.1 Kernel pinning

The manifest carries `kernel-version 6.12` (from the machine file) and a `modules` line (empty). `hubos-ctl update` prints both (`update: kernel version 6.12, modules:`) and **refuses a bundle whose signed manifest has no `kernel-version` line** (`REFUSED: manifest has no kernel version line`; test 4, bundle `v2-nokernelversion`). The module list is only printed in this slice: there are no modules to build or check. The rule in `HUB-OS.md` (out-of-tree modules are listed in the signed manifest and covered by the boot tests) has no test yet beyond that.

### 3.2 The interrupted update (test 8)

The update tool prints a line at each step, and the runner waits for a **log line** and then sends `SIGKILL` to QEMU:

| Interrupted at the line | Meaning |
|---|---|
| `update: fetching rootfs.sqsh` | during the download |
| `update: wrote 8 of N MiB to slot a` | during the write to the other slot (the write is in 4 MiB pieces with a line after each) |
| `update: root written and verified` | after the write, before the kernel is copied |
| `update: kernel installed` | after the kernel copy, before `BootNext` is set |

After each kill QEMU is started again on the same disk and variable store. Every time the machine booted the confirmed slot (`slot=b release=2`, first in `BootOrder`, no `BootNext`). Then a clean update to release 7 was made: the machine rebooted into slot A, release 7, and confirmed it.

**What this does not show:** `kill -9` of QEMU stops the guest; the host still has everything the guest already wrote (QEMU's cache), so it tests the update's **order of steps**, not what a real disk does when the power fails mid-write.

### 3.3 The unexplained hang

The prototype saw one start in about twelve stop silently after `BdsDxe: starting Boot0001`. The runner waits for a known line (`HUBOS: handing over to s6-svscan`, 150 s) after every start and every reboot. **Rule:** if the line does not come, the hang is recorded (its number, the step it happened in and the saved serial log in `$WORK/hangs/`), QEMU is killed and that step is retried **once**; **a second hang in the same step fails the run**. At the end the runner prints `QEMU hangs seen and retried: N; every hang: ...` with every hang listed. No real hang has happened in any run. The retry code is exercised by a **test hook** (section 3.8). The cause of the earlier hang stays UNKNOWN, and not seeing it does not mean it is gone.

### 3.4 One kernel per slot (the slot does not depend on the firmware's load options)

Before: each boot entry carried its command line as load options, while the kernel's built-in command line named slot a. A firmware that drops load options would have booted slot b's kernel with slot a's root. Now:

- `build-kernel.sh` builds **two kernels**; each has its own slot and root built in: `kernel-a.efi` (`root=PARTLABEL=hubos-root-a hubos.slot=a`) and `kernel-b.efi` (`...-b ... hubos.slot=b`). Everything else is identical; both files are 4,117,504 bytes and their hashes differ.
- The bundle carries both; the signed manifest lists both with hash and size. `hubos-ctl update` refuses a manifest that does not list both, but **fetches and installs only the other slot's kernel** (`kernel-$OTHER.efi`).
- **None of the three boot entries (a, b, recovery) has load options.** The recovery entry boots a **separate recovery kernel** (section 3.7), so it needs no command line either.
- A machine whose entries were made by an earlier image (with load options) keeps those entries; `ensure-entries` only creates missing entries. No such machine exists yet.

### 3.5 Free space on the boot partition

`hubos-ctl update` now mounts the boot partition and checks its free space **right after the hashes are verified and before anything is written**: it needs the size of the new kernel plus 1 MiB. If there is not enough room it stops with `FAILED: not enough free space on the boot partition (have N bytes, need M); nothing was written, the existing kernel and slot X are untouched` (exit code 2), without touching the other slot's root, the existing kernel or the boot entries. A leftover `*.new` file of an interrupted earlier update (a temporary copy, never the kernel itself) is removed first. The partition is unmounted when the tool exits, on every path. The copy itself still goes to `kernel-X.efi.new` and is moved into place only after a sync; if the copy fails the temporary file is removed.

### 3.6 The update floor: only up, confirm refuses below it, `rollback` goes down on purpose

- **The floor only goes up.** `hubos-ctl confirm` writes the larger of the old floor and the running release into `/config/hubos/state/min_version`.
- **Confirm refuses a slot whose release is below the floor** (`confirm: REFUSED: release 2 of slot b is below the floor 7; BootOrder and the floor are unchanged (to go back on purpose: hubos-ctl rollback REASON)`, exit code 2). Nothing changes: the slot is not made first in `BootOrder` and the floor is not touched. Test B1: after the rollbacks and the interrupted updates (floor 7, release 7 in slot a) the older slot b (release 2) is booted by hand with `BootNext`; its automatic confirm step prints the refusal, a manual `hubos-ctl confirm` returns 2, slot b did not become first in `BootOrder`, the floor is still 7, and an update to release 5 is refused (`below the floor 7`; test A).
- **`hubos-ctl rollback REASON`** is what the owner runs *on purpose* to go back to the running older release. It needs a reason (without one it prints usage and returns 2), needs the running slot to have been booted through its own entry, **lowers the floor to the running release**, **makes the running slot first in `BootOrder`**, and **logs** one line in `/config/hubos/state/rollback.log` with the time, slot, release, `floor 7 -> 2`, the new first entry and the reason. Test B2: usage without a reason; with a reason the output is `rollback: floor 7 -> 2; slot b is now first in BootOrder; reason logged: ...`, `min_version` is 2, slot b is first, and the log line holds the reason. It does not install anything and does not touch the other slot. (The clock of the test image is whatever the firmware gave it; the log's time is only as good as that.)
- A rollback boot by the firmware (a failed trial) never changes the floor, because it boots a slot that is already confirmed.

### 3.7 The separate recovery kernel

**What it is.** `kernel-recovery.efi` is a third kernel built with the same configuration as the slot kernels but with another initramfs and a command line that has no `root=` and no `hubos.slot=` (`console=ttyS0 ro loglevel=4 panic=5`). Its stage 0 (`image/stage0/recovery-init`) mounts nothing of either slot: it mounts `/proc`, `/sys`, `/dev`, `efivarfs`, the config partition **read-only**, the data partition **read-write** (room for a bundle; without it a bundle goes to RAM), brings up the network with DHCP, prints `HUBOS: RECOVERY MODE ...` and leaves a bare terminal (`exec setsid cttyhack /bin/sh`). It **arms the hardware watchdog and feeds it** (section 3.7a) and never reboots by itself. Its initramfs (6.3 MB kernel in total) holds busybox (all applets), `hubos-ctl`, `efibootmgr`, `signify-openbsd`, **the update keyring (`/etc/hubos/keys/*.pub`, section 3.12)**, e2fsprogs (`e2fsck`, `mke2fs`, `tune2fs`, `resize2fs`, `dumpe2fs`, `debugfs`, `chattr`), `findfs`, `blkid`, the network script and the libraries they need, copied from the base root and the unpacked tools at build time (`tools/image/recovery-list.py`). BusyBox's shell prefers its own applets over files in `PATH`, and its `findfs` and `mke2fs` are not the full programs (busybox `findfs` has no `PARTLABEL=`), so `/etc/recovery.rc` (read through `ENV`) aliases `findfs`, `mke2fs` and `blkid` to the real ones, and `hubos-ctl` calls `/sbin/findfs` by path.

**The entry.** The `hubos-recovery` boot entry **always** points at `\EFI\hubos\kernel-recovery.efi`, with **no load options**, and sits in `BootOrder` **directly after the two slot entries** (`BootOrder: 0007,0008,0009,...` in the tests). `ensure-entries` deletes and recreates a recovery entry that points anywhere else. Recreating the entry at every confirm is gone (OVMF keeps an entry that is in `BootOrder`; test R0: the entries present when slot b booted after the update were `hubos-a hubos-b hubos-recovery`). Recovery does not use a slot, so it is the same recovery kernel after an update, during an unconfirmed trial, after a rollback and with both roots destroyed; the tests compare the command line and release line of the recovery shell and they are identical every time.

**Where the recovery kernel comes from, and when it is installed (new this round).** The recovery kernel is **carried inside every release's root**, at `/usr/lib/hubos/recovery/kernel-recovery.efi` with `recovery.version` next to it. The signed manifest lists its hash (`kernel-recovery.efi sha256 ... size ...`) and `recovery-version N`; both lines are optional, one without the other is refused (`REFUSED: the manifest lists the recovery kernel only in part`), a non-numeric version is refused.
- **`hubos-ctl update` no longer touches the recovery kernel or the boot partition's recovery files.** After it writes the root and verifies it, it mounts the written root read-only and compares the file inside with the manifest (hash and version). A mismatch is `REFUSED: the recovery kernel inside the new root does not match the manifest ...; BootNext is not set` (test C3: a correctly signed manifest with a wrong hash). A release with no recovery kernel says `the manifest has no recovery kernel; recovery left alone`.
- **`hubos-ctl confirm` installs it, after a healthy boot,** only when the root's `recovery.version` is **greater** than the installed `\EFI\hubos\recovery.version`: it mounts the boot partition, checks the free space first (the kernel plus 1 MiB; if it does not fit it says so and installs nothing), copies to `kernel-recovery.efi.new`, syncs, compares the copy's hash with the source, renames over `kernel-recovery.efi` (an atomic rename on FAT) and then writes the version file the same way. Every failure is reported and **never fatal**: the boot is already confirmed and the old recovery kernel is untouched or was replaced whole. The same step runs when the slot is already the confirmed one (a repeat boot), so an install that was interrupted is retried at the next healthy boot.
- **A trial boot that never confirms leaves the old recovery kernel in place** (test C2: release 12 carries recovery version 3, its hubd never becomes healthy, the boot is rolled back; the boot partition still has version 2 and the version-2 file).
- *Test C1:* release 9 without a recovery kernel (unchanged, "this release carries no recovery kernel"); release 10 with recovery version 2: right after the update the boot partition still holds version 1, after the trial boot's confirm it holds version 2 and the new file; release 11 with version 2 again (the same file): "version 2 is the same file as the installed one; left alone". The rule is in the next paragraph and is tested by C5.

**The install rule at confirm (changed this round).** The confirm step installs the recovery kernel from the new root when **its file differs from the installed one AND its version is not lower than the installed one** (never a downgrade). Three cases: a different file with a higher version installs; a **different file with the same version installs too** (a key-rotation release that forgot to bump the version no longer leaves the old keyring in recovery: `confirm: recovery kernel version 5 installed (was 5)`); a lower version never installs (`version 4 is lower than the installed 5; never a downgrade, left alone`); the same file is left alone (`is the same file as the installed one; left alone`). Before this round the rule was "version strictly higher", which silently skipped the second case. Test C5 (after the key rotation, signed with key 2): release 25 (version 5, a changed file) installs; release 26 (version 4, another file) does not; release 27 (the file of release 25 again) leaves it alone. The free-space check, the temporary name, the hash comparison and the atomic rename are unchanged. Unverified: a downgrade on purpose is not possible any more through the normal path (it would need the recovery shell or a hand copy); nothing in the tests does that.

**Recovery can install a bundle (new this round).** `hubos-ctl update BASE [SLOT]` works in the recovery shell. It installs into the slot the owner names (default `a`), with the same checks as in a running slot: unsigned, tampered or wrong-key manifests and a root that does not match its hash are refused; the manifest must name both slot kernels. What "not newer" means is different, because no release is running in recovery: a release **below the floor** (the highest release ever confirmed) is refused (`REFUSED: version 2 is below the floor 11 (recovery installs only releases at or above the floor)`); the floor's own release may be installed again, because reinstalling the last good release into a broken slot is the main use. It writes the target slot's root and kernel, sets `BootNext` to that slot (a trial boot, as for an update), and **clears the boot-failure counter** (a fresh install starts with a clean count, section 3.9). It does not change `BootOrder` or the floor: the confirm step of the new slot does. In a running slot `update BASE SLOT` accepts only the other slot (`REFUSED: slot a is the running slot`). In recovery the bundle is fetched into the data partition (`/data/update`), or into RAM if there is no data partition.
- *Tests R3 and R4:* in the recovery shell with both roots destroyed, an unsigned bundle, a tampered manifest and a bundle below the floor (11) are each refused with exit code 2 and neither root and no `BootNext` is touched (R3); release 13 is installed into slot a, the machine reboots, boots release 13 and confirms it (R4).
- The install is written for a human at the console. There is no keyboard test (the tests use the serial console).

**What this does not show:** a real firmware (OVMF only); a recovery boot on a machine whose ESP is full or whose config partition is damaged (the shell would still come up; not tested); a keyboard; the network path other than QEMU's DHCP; an install from a bundle larger than the data partition when there is none (it would fill RAM).

### 3.7a The watchdog in the recovery kernel, and the recovery agent in a TEST recovery kernel

**The watchdog (new this round, test W1).** Before this round a recovery kernel that hung stayed hung. Now `recovery-init` opens `/dev/watchdog` at the very start (the countdown begins, with the driver's own default timeout) and, as soon as the config partition is mounted read-only, sets the machine's timeout and starts a small **feeder**: `watchdog -F -T <WATCHDOG_TIMEOUT> -t 5 /dev/watchdog` (the busybox applet, in the background, fed every 5 s). **The value** is the one stage 0 of the slots uses: `WATCHDOG_TIMEOUT` from `/config/hubos/node.conf`, default 180 s, with the same rule (`check-timers.sh`, now also in the recovery kernel; a refused pair falls back to 120 s and 180 s). In the test image it is 60 s (test 15 sets it). If the recovery shell or the feeder hangs or is killed, the machine resets after that time and goes back through stage 0 of the slot kernel (which counts a boot; with broken slots it ends in recovery again after the failed boots). Nothing was missing in the recovery kernel's busybox: the `watchdog` applet and the `i6300esb` driver are there (the same kernel configuration as the slots). TESTED (W1, in test 13, both roots garbage): the feeder runs with `-F -T 60 -t 5`; a normal recovery stays up for longer than the timeout (uptime above 80 s with a 60 s timeout, no reset); with `kill -9` on the feeder the machine reset after about the timeout (the line `STAGE0: start` of a slot kernel appears) and came back to the recovery shell. UNVERIFIED: real hardware watchdogs (only QEMU's `i6300esb` was used), and a hang of the whole kernel (only the feeder was killed).

**The recovery agent in a TEST recovery kernel (new this round, test T18).** `tools/image/experiments/recoveryagent` (section 3.11 and `docs/proposals/recovery-and-out-of-band.md`) now has a real backend (`-backend hubos`: status from `/etc/hubos-release` and `hubos-ctl status`; install = `hubos-ctl update BASE SLOT`; clear failures = `hubos-ctl clear-failures`; logs = the agent's own log) next to the fake one. `build-kernel.sh` builds a **second recovery kernel**, `kernel-recovery-agent.efi`, when `RECOVERY_AGENT_BIN` (the static agent, `CGO_ENABLED=0 go build`) and `RECOVERY_AGENT_KEYS` (management public keys, not the update key) are set; the normal `kernel-recovery.efi` and the slot kernels are not touched by that build. The test kernel carries `/usr/sbin/recovery-agent`, the management keys in `/etc/hubos/mgmt/` and a start script (`image/stage0/recovery-agent-start.sh`) that `recovery-init` runs after DHCP only if the file exists (a hook that does nothing in the normal recovery kernel). The agent listens on port 8480 of the recovery kernel's address; QEMU forwards a host port to it for the test. **API (from the proposal):** `GET /v1/status` (open), `GET /v1/challenge` (a one-time nonce), and signed requests `POST /v1/install` (`{"Slot":"a|b","BaseURL":"..."}`), `POST /v1/clear-failures`, `GET /v1/logs`, with the header `Authorization: HubOS-Sig nonce=HEX, sig=BASE64` (a signify-format Ed25519 signature over protocol name, method, request path, nonce and the hash of the body).

The release label inside the test kernel is still `recovery-1`: `RECOVERY_VERSION` in the machine file wins over the environment, only the bundle's `recovery-version` decides what the confirm step installs (noticed while writing the test). **Not shown:** the agent is **not in any image**; no TLS; the address is DHCP (QEMU's user network, 10.0.2.15, forwarded by the host); nothing supervises the agent in the recovery kernel (if it is killed it stays dead, the shell stays); the install request blocks until the install is done (about a minute); the management key handling (where the private key lives on the hub) is not designed; real hardware, a real network and the hub side (hubd talking to the agent) are untested.

A crash in the middle of a shell command on the guest cannot be retried (the step has side effects that are not repeatable): it is listed in the RESULTS and fails the run at once with a clear message. - `twice`: `CRASH 1 (first boot [forced ...]): QEMU died from signal 11 (segmentation fault)`, `CRASH 2 (first boot (retry) [forced ...])`, then `the machine hung or crashed twice in the same step (first boot); the run fails`; test 1 failed, tests 2 and 3 were skipped (`run stopped by a repeated hang`), `--- FAIL: TestImage`; the RESULTS list both crashes.

### 3.9 The boot-loop breaker

**Why it is needed (TESTED with OVMF last round, tests C4 and C5; BELIEVED for real firmware).** The claim "UEFI falls through to the next `BootOrder` entry only when the loader cannot load the file, not when a loaded kernel then fails" is **correct for OVMF**: with both slot roots destroyed and `BootOrder: a, b, recovery` the firmware started `hubos-a` 14 times in 100 seconds and never `hubos-b` or `hubos-recovery`; with `kernel-a.efi` removed it logged `failed to load Boot0007 "hubos-a"` 14 times and started `hubos-b` 14 times, and recovery never. So a confirmed slot that loads and then fails loops forever, and the watchdog only turns a hang into a reboot. (Those two experiments are not in the suite any more: with the breaker the loop ends after three boots, which tests P1 below show instead.)

**How it works (built).**
- **The counter is a set of EFI variables.** Vendor GUID **`a0b7c0f5-4e7a-4d2b-9c61-5f0a1e3d8b72`** (made for Hub OS; not registered anywhere). Each counted failed boot is one variable named `HubosBootFail1`, `HubosBootFail2`, ..., attributes NV+BS+RT (7), a 1-byte value `1`. **The count is the number of such variables.** Why not one variable holding a number: files in `efivarfs` are immutable, changing an existing variable needs `chattr -i`, and the tiny stage 0 has no `chattr`; *creating* a variable needs nothing. Stage 0 only ever creates; the root's tools delete (with `chattr -i`). Reading is a glob, so no read-modify-write and no partial update. (`tail` cannot seek in `efivarfs`; an earlier try that way read 0 for a count of 1.)
- **Stage 0 of the slot kernels, at every boot, before the root is mounted:** counts the variables (`STAGE0: failed boots counted so far: N (limit L)`); if `N >= L` it finds the recovery entry (a `Boot####` variable whose description is `hubos-recovery`), writes `BootNext` to it and reboots (`STAGE0: 3 failed boots in a row (limit 3): starting the recovery shell (entry 0009) instead of booting slot a`); otherwise it creates the next variable and boots. So the counter is raised at the start of a boot and a boot that dies on the way (stage 0 refuses the root, no `/sbin/init`, init hangs and the watchdog resets, the confirm timeout, a power cut) leaves it raised.
- **`hubos-ctl confirm`** (after hubd is healthy) deletes all the variables (`confirm: boot-failure counter cleared`), on the confirming path and on the "already the confirmed slot" path. A confirm that is **refused** (release below the floor) does not clear it. `hubos-ctl clear-failures` clears it by hand; the recovery install clears it. `hubos-ctl status` shows `boot-failures=N limit=L`.
- **N is `BOOT_FAIL_LIMIT` in the node config** (`/config/hubos/node.conf`, default 3; the machine build file's value is written there by `build-disk.sh`). **Stage 0 reads it:** it mounts the config partition read-only for a moment (the same lookup by GPT name it uses for the root) and reads three keys with `sed`, without running the file. A missing, non-numeric or zero value means 3. If the config partition cannot be read, all three settings take their defaults (3, and 120 s and 180 s for the timeouts, section 3.10) and stage 0 says so.
- **After recovery:** the shell shows `boot-failures=3 limit=3`. The owner reinstalls a release from the shell (which clears the counter) or runs `hubos-ctl clear-failures`; until then the machine does not leave the recovery path by itself, because stage 0 sends every boot of the slot back to recovery while the count is at the limit.

**What happens when the variable cannot be read or written, and why (the direction of failure).**
- *Cannot read* (no `efivarfs`, or no firmware variable support): stage 0 says `WARNING no EFI variables (efivarfs not mounted); the boot-loop breaker is OFF for this boot; booting normally` and boots. A missing variable is a count of 0.
- *Cannot create the next variable* (store full, firmware refuses): `WARNING cannot write the failure counter; the boot-loop breaker is OFF for this boot; booting normally`.
- *The count is at the limit but the recovery entry is missing or `BootNext` cannot be written:* a warning, and **boots normally** (without creating more variables, so a stuck machine does not fill the store).
- So **stage 0 fails toward booting.** Reason: the breaker is a safety net for a rare event; a machine whose firmware variables do not work (no counter possible) would otherwise be sent to a bare recovery shell on **every** boot, and a rack machine without a keyboard could not come up at all. The cost is that on such a machine a boot loop is not stopped (UNKNOWN how common; not tested because no way was found to make OVMF refuse the write).
- *Cannot clear after a healthy boot* (the opposite failure): the confirm step prints `WARNING cannot clear the boot-failure counter` and goes on, because the boot is confirmed. The leftover count then rises with each boot and after three would send a healthy machine to recovery, where `hubos-ctl clear-failures` clears it. That is a failure **toward recovery**, chosen because it is loud and fixable from the shell and because it needs the store to accept writes at stage 0 and refuse deletes at the confirm step, which is unlikely (UNKNOWN on real firmware).
- *Not tested:* any of these failure paths (the test image cannot make OVMF refuse a variable write). **BELIEVED** from reading the code only.

**Tests (section 3 table):** **P1** three kinds of failing boot, each installed into slot a from the recovery shell: a garbage root, a root with no `/sbin/init`, and a root whose init runs but whose hubd never gets healthy (confirm timeout). For each, stage 0 counted `0,1,2,3` over four boots (three failing boots, then recovery at the fourth) and the shell showed `boot-failures=3 limit=3` and the same recovery kernel as always. **P2** the counter survives `kill -9` of QEMU: a trial boot is killed right after stage 0 counted it, QEMU is started again on the same variable store, and stage 0 reads `failed boots counted so far: 1`; the healthy boot then clears it; this is also a normal update trial that does **not** trip the breaker. **P3** a good boot after recovery works: the recovery install clears the counter and the machine boots and confirms the release. The bad-boot tests 6a to 6d also assert that after each rollback the counter is 0 (so a failed trial plus its fallback boot never trips the breaker: they count at most 2).

**Not covered:** a hang of init is covered by 6d (watchdog reset) but not as a third kind in P1 (it takes 60 s per boot); NVRAM wear and the size of the variable store on real firmware (each failed boot writes one variable, each confirm deletes them: UNKNOWN); a real firmware that deletes unknown variables at boot or refuses variables with this GUID (UNKNOWN).

### 3.10 Per-machine timeouts

The confirm timeout (how long an unhealthy trial boot waits before it gives up and reboots) and the watchdog timeout (how long the hardware watchdog waits for a feed) are per-machine settings in the node config (`CONFIRM_TIMEOUT`, `WATCHDOG_TIMEOUT` in `/config/hubos/node.conf`), with the **real defaults 120 s and 180 s**; the test image's machine file sets **30 s and 60 s**.
- **Where they are used.** Stage 0 reads them (section 3.9), arms the watchdog with the machine's timeout (it starts the `watchdog` applet with `-T`, then kills it without the magic close; with `nowayout` the countdown keeps running with the new timeout; checked once by hand, not in the suite: with `WATCHDOG_TIMEOUT=75` in the node config a hung trial boot was reset 79 s after stage 0's "switching" line, more than the 60 s of the machine file; the expected time for 60 s was not measured), and exports `HUBOS_CONFIRM_TIMEOUT`, `HUBOS_WATCHDOG_TIMEOUT` and `HUBOS_BOOT_FAIL_LIMIT`. The confirm service waits that long, and the `wd` service feeds the watchdog with that timeout. The kernel's first heartbeat (before stage 0 has read the config) is the machine file's `WATCHDOG_TIMEOUT`.
- **The rule** (`image/rootfs/usr/lib/hubos/check-timers.sh`, one file used everywhere): the watchdog timeout must be **more than the confirm timeout plus 15 s**. Otherwise a slow unhealthy trial boot is reset by the watchdog before it prints its failure and rolls back cleanly. 30/45 is refused (exactly confirm + 15), 30/46 is fine; non-numbers are refused.
- **At build time:** `build-kernel.sh` and `build-disk.sh` refuse a machine file or node config that breaks the rule, with the message, and make nothing (test D1: a machine file with 60/70).
- **At boot:** stage 0 checks the pair it read. A bad pair is **refused**: the message `STAGE0: REFUSED: watchdog timeout 40s must be more than the confirm timeout 30s plus 15s (more than 45s); ...` is printed and the **defaults 120 s and 180 s are used** (the defaults satisfy the rule themselves). It does not refuse to boot: the node config is shared by both slots, so refusing would loop on both. Test D2: node config 30/40 → refused, defaults used, the watchdog feeder runs with `-T 180`; node config 20/50 → used by stage 0, the confirm step and the feeder (`-T 50`); restored to 30/60 afterwards.
- *What this does not show:* a node config edited so that only one of the two values is set (a missing value takes its own default, then the pair is checked: 30 with the default 180 is fine; 130 with 180 is refused); a real machine's boot time against 120 s (UNKNOWN: a slow real boot may need longer; the owner sets it per machine).

### 3.11 Proposal only: unattended recovery for machines without a keyboard

**Nothing here is built.** Today the recovery shell needs a person at a console (or serial) to type `hubos-ctl update ...`. For rack machines with no keyboard the idea is that recovery repairs itself, or at least reports.
1. **Bring up the network** (already done: DHCP, or the static settings if the recovery kernel is taught to read them from the config partition; today DHCP only).
2. **Report to the hub.** The recovery kernel would send "node X is in recovery, boot-failures N, last slot release R" to the hub (a one-line message to a port `hubd` listens on, or `hubd` notices a node whose normal port stays down but whose recovery port answers). `HUB-OS.md` says there are no phone alerts, so the report would be a state in the panel ("2 of 4 up, 1 in recovery").
3. **Optionally fetch and install the latest signed bundle** from the hub (or the NAS): `hubos-ctl update BASE a` with the base URL from the config partition, then reboot. The tools already exist; what would be new is an `s6`-less "recovery autopilot" script run by `recovery-init` after the network is up, with a delay (so a person who is there can interrupt it), a retry limit and a rule for which slot.

**What it needs (all open):** where the recovery kernel finds the hub's address and the bundle location (the config partition may be what is broken; a copy inside the recovery kernel would be stale); which bundle (the newest, the floor's release, or the last one that was confirmed; the hub would have to offer it); which slot (the one that failed, or the other; a rule for a machine where both fail); a stop rule so that a bundle that cannot boot is not installed in a loop (the failure counter already counts; recovery's own count would need to survive); how long to wait before acting; and a way for the owner to switch the autopilot off per machine.
**Risks:** an automatic install overwrites a slot that may hold the owner's only working release (the other slot should stay untouched, but a machine whose **both** slots are broken has nothing to lose); a bad or old signed bundle served by mistake is installed without a human looking (the floor stops a release below the floor, but not a bad one above it); the report and the fetch trust the network (the bundle is signed, the report is not); a hub that is itself down cannot answer, so the machine would sit in recovery anyway; secrets must not be put in the recovery kernel (it is on the open boot partition); and an endless recovery-reboot-recovery loop if the installed release fails the same way again.
**Questions for the owner** are listed in the reply to this round and in section 8.

### 3.12 The update keyring and key rotation

**What changed.** The single public key `/etc/hubos/update.pub` is gone. Every root, and the recovery kernel, has a **keyring**: the folder `/etc/hubos/keys/`, with one `NAME.pub` file per accepted key (the build names a file after the first 16 hex digits of its sha256, so two keys never collide). `hubos-ctl update` (in a running slot and in the recovery shell) accepts a manifest signed by **any** key in the keyring: it tries each `*.pub` with `signify-openbsd -V` and stops at the first that verifies. It prints `update: signature OK (key 3f9a..., 2 key(s) in the keyring)`; with no key in the folder it refuses (`REFUSED: there is no update key in /etc/hubos/keys`); with no match it refuses with the old words (`REFUSED: bad signature (manifest not signed by any of the 1 key(s) in /etc/hubos/keys, or changed)`). Still one signature per manifest (`manifest.sig`): the keyring only decides who may sign, nothing is signed twice. Build: `build-root-image.sh` puts the keys of `KEYRING_PUBS` (default: the one public key argument) into the root; `build-kernel.sh` puts `UPDATE_KEYS` (default `UPDATE_PUB`) into the recovery kernel; both are inputs of the recovery kernel's stamp, so a new key set rebuilds it (about a minute). No key is in the repo.

**The rotation procedure** (key 1 is in use, key 2 is the next one; every step is a normal release through the normal update):
1. Make key 2 offline (`signify-openbsd -G`). Keep both secret keys out of the repo and off the machines. Only the public keys travel.
2. **Release N**, signed with **key 1**, carrying **both public keys** in its root's keyring (`KEYRING_PUBS="key1.pub key2.pub"`) and a **recovery kernel built with both keys** and, as a rule of thumb, a **higher `recovery-version`** (`UPDATE_KEYS="key1.pub key2.pub"`, `RECOVERY_VERSION` one more; since this round the confirm step also installs a changed recovery kernel at the same version, so a forgotten bump no longer leaves recovery on the old keys, but bump it anyway: it is the visible record of the change and it is what protects against a downgrade). Machines accept it (signed with the key they know). At its confirm step the new recovery kernel is installed on the boot partition (section 3.7). Now the slot and the recovery kernel know both keys.
3. **Wait** until every machine runs N or later (a machine that is still on a release before N cannot verify a release signed with key 2). Keep release N, signed with key 1, available until the rotation has reached every machine and every recovery kernel.
4. **Release N+1**, signed with **key 2**, carrying **key 2 only** (`KEYRING_PUBS=key2.pub`) and a **recovery kernel with key 2 only**, again with a higher `recovery-version`. Machines on N accept it (they know key 2). After its confirm, key 1 is gone from that slot and from the boot partition's recovery kernel; a bundle signed with key 1 is refused from then on.
5. Only in a **later** release is key 1 dropped for good everywhere: until both slots have been updated past N+1, the older slot's root still has the old keyring (a rollback boot returns to it, which is consistent: that release also knows key 2 if it is N or later).
What the tests show (test K1/K2, section 3 table): a key-2 bundle is refused while only key 1 is known; a release signed with key 1 that carries key 2 is accepted, confirms, and installs a recovery kernel that knows both (for example version 2 -> 4); after it a bundle signed with key 2 is accepted and drops key 1 (recovery kernel with key 2 only, again a higher version); a bundle signed with key 1 is then refused (`bad signature ... any of the 1 key(s)`); the recovery shell uses the keyring of the recovery kernel on the boot partition (key 2 only): it refuses the key-1 bundle and installs a key-2 bundle into slot b, which boots and confirms.

**What happens when only the new key is in the slot but an old recovery kernel is installed.** The recovery kernel's keyring is the one it was built with, and it changes only when a release with a **different recovery kernel file and a version not lower than the installed one** is confirmed. If a release carries key 2 but its recovery kernel is the same file, or has a lower version, or the install fails at the confirm step (the message `confirm: recovery kernel NOT installed: ...` or `... left alone` says which) the recovery kernel on the boot partition keeps only key 1. A machine whose slots are then both broken **cannot install a release signed with key 2 from the recovery shell** (`REFUSED: bad signature`; shown by test R3, which offers a key-2 bundle to the original key-1 recovery kernel). The way out is the normal path: any slot that still boots verifies with its own keyring, and the confirm step of a release that carries a newer recovery kernel installs it; or install a release that is signed with key 1 (keep release N for this). So: **put the new recovery kernel into every release that changes the keyring** (bump `recovery-version` too) and check the confirm line `recovery kernel version M installed (was M-1)` on one machine before dropping key 1.
**Not covered:** a revocation list (the only way to distrust a key is to ship a release without it); a machine that missed release N and is two keys behind (it needs release N first); signing-key storage and backup (outside this repo).

### 3.13 The wofi menu (why hubd passes `--height` and never `--lines`)

The desktop experiment found hubd's menu empty under driftwm's real display backend (only wofi's search box showed). Cause found this round, in the guest: wofi **1.4.1**, started with `--lines 12`, asks the compositor for a layer surface of 720x1, then 720x5, and prints `Gtk-CRITICAL ... gtk_widget_set_size_request: assertion 'height >= -1' failed` (`WAYLAND_DEBUG=1`: `set_size(720, 1)`, `set_size(720, 5)`, the critical, later `set_size(720, 281)` and driftwm's `configure(720, 281)`: the compositor does what is asked). The source (`src/wofi.c`, `update_surface_size`) shows why: with `lines > 0` the height starts at 1, becomes `max_height * lines + 5` while `max_height` (the height of one row) is still 0 because no row exists yet, and the list is then given the size `height - entry height`, a negative number. Rows are inserted later, but the list is never drawn (a screenshot with the 281 px surface shows the search box and black below). With `--height 480` (and no `--lines`) wofi sizes the surface once and the list is drawn. This is a **wofi 1.4.1 bug in its `--lines` path on a layer-shell surface**; it is not known whether newer wofi versions fix it. The first investigation (`docs/bar-findings.md`, `docs/hubd-slice2.md`) ran wofi on a virtual X display, where wofi does not use layer-shell and this code is not run, so it never saw the problem. **Fix:** `hubd menu` passes `--height 340` (a new flag `--height PIXELS`, 100 to 4000; 340 is the search box and about 12 rows of the example style) and never `--lines`. Tests: `cmd/hubd/menu_test.go` (the arguments contain `--height` and not `--lines`, the flag is honoured and a silly value is refused) and test H3 of the hub image (the menu opened by a click on the Waybar item has its list drawn). The `wofi-fixed` wrapper of the experiment is gone.

## 4. systemd rules in the image, and the libraries that remain

**The rules (owner's decisions of 2026-10-03, `HUB-OS.md`):** systemd programs are never installed or run; `libsystemd0` and `libudev1` are tolerated for now as plain libraries; the build pins the systemd packages to never install and tests for them; finished images have no apt, PAM modules or procps.

- **The pin.** `image/apt/no-systemd.pref` (the text of `docs/proposals/systemd-libraries.md` section 1.4) is put into `/etc/apt/preferences.d/hubos-no-systemd` before the first package is installed. The test compares the file in the built root with the file in the repository and checks that it lists all seven packages with `Pin-Priority: -1`. **What this does not show:** the package list of this machine (`s6`, `execline`, `busybox-static`, `libc6`) pulls in none of the pinned packages, so the pin has never *had to refuse* anything here; its effect (apt taking `dbus-x11` instead of `dbus-user-session`) was only simulated in the research document, not in this build. It matters when PipeWire, WirePlumber or GTK programs are added.
- **The build test.** It fails if any of `systemd`, `systemd-sysv`, `libpam-systemd`, `dbus-user-session`, `udev`, `systemd-timesyncd`, `systemd-resolved` is marked installed in the root's dpkg status; if a systemd program (`systemd`, `systemd-*`, `systemctl`, `journalctl`, `udevadm`, `udevd`), a unit file (`*.service`, `*.socket`, `*.target`, `*.timer`) or a unit or udev directory (`/etc/systemd`, `/usr/lib/systemd`, `/lib/systemd`, `/etc/udev`, `/usr/lib/udev`, `/lib/udev`) is in the root; and, in the booted image, if any process has a name starting with `systemd` (`/proc/*/comm`).
- **The strip step.** `mmdebstrap --variant=minbase` produced a root that has **no `apt` and no `libapt-pkg6.0t64`** at all (the research document tested a `debootstrap` root, which has both), so for those two the step has nothing to remove and says so. It removes the files of `procps`, `libproc2-0`, `libpam-runtime`, `libpam-modules`, `libpam-modules-bin`, `login` and `passwd` (hundreds of files, including their manuals). It does **not** do step B of the research document: `lslogins`, `lsblk`, `findmnt`, `logger` stay, so do `libsystemd0` and `libudev1`. `dpkg`, its status file and `libpam0g` stay.
- **The library check.** `check-libs.sh` runs `ldd` inside the root on every ELF file in `/usr` (and `/bin`, `/sbin`, `/lib` where they are real directories; here they are links into `/usr`). The build fails on any `not found`. The test also shows the check can fail: it deletes `libmount.so.1` from an unpacked copy and expects `libmount.so.1 => not found`. **This is only link-level.** Nothing proves the stripped programs work beyond what the QEMU tests do.
- **What the two libraries still do.** They are in the root (`/usr/lib/x86_64-linux-gnu/libsystemd.so.0(.38.0)` and `libudev.so.1(.7.8)`); the test lists them. They are kept by decision.

**Not tested:** real logins through `sshd` without PAM modules (no `sshd` is in this image; the research document ran only `sshd -t`); `su`, `login` or password change with no PAM modules.

## 7. Changes from the prototype (and why)

- The root is made with `mmdebstrap` pinned to a dated snapshot, as the owner decided (the prototype used `debootstrap` against the live archive for its tests and `mmdebstrap` for the reproducibility check).
- Unit files and rules of systemd and udev are removed from the root after the build; otherwise the "no systemd unit directory" check cannot pass (they come from `e2fsprogs`, `util-linux`, `dpkg`).
- `hubos-ctl update` refuses a manifest with no `kernel-version`, and prints a line at each step (the write is in 4 MiB pieces) so the runner can interrupt it at known lines.
- The runner waits for known log lines instead of fixed seconds, and retries a hung start once.
- `libbsd0` (needed by `signify`) is unpacked with the tools, not taken from the host.

- (2026-10-03, second round) The floor only goes up; recovery is recognised by the entry label, not by load options; one-kernel manifests are refused; the hang retry is exercised by `HUBOS_TEST_FORCE_HANG`; the recovery entry's behaviour (dropped by OVMF at reboot, recreated by the confirm step for the running slot) is tested and documented, with fixes proposed but not built.
- (2026-10-04, second round) The recovery kernel arms the hardware watchdog and feeds it (section 3.7a, test W1); a TEST recovery kernel carries the recovery agent (`RECOVERY_AGENT_BIN`, test T18); `check-timers.sh` is also in the recovery kernel; tests wait on the right text: test 15 no longer depends on a stage-0 line that the kernel's own `watchdog did not stop!` message can cut in two.

## 8. Things noticed while building this

- (Fixed 2026-10-03, section 3.6) `hubos-ctl confirm` used to be able to lower the floor.
- (Fixed 2026-10-03, section 3.7) recovery used to depend on load options, then on the slot that booted last. It is now its own kernel and needs no slot.
- (Fixed 2026-10-03, section 3.13) the empty wofi menu of the desktop experiment: a wofi 1.4.1 bug in its `--lines` path on a layer-shell surface; hubd now passes `--height`.
- (Fixed 2026-10-03, section 3.9) a confirmed slot that loads and then fails used to loop forever on OVMF; the boot-loop breaker sends the machine to the recovery shell after 3 failed boots.
- `tail -c +N` cannot read an `efivarfs` file (`Illegal seek`), and `efivarfs` files are immutable (writing an existing variable needs `chattr -i`); busybox has no `chattr`. The counter is therefore one new variable per failure.
- Busybox's shell and applets shadow the real `findfs` (no `PARTLABEL=`) and `mke2fs`; the first recovery tests failed on this until `hubos-ctl` called `/sbin/findfs` by path and `recovery.rc` aliased the real programs.
- `mmdebstrap --variant=minbase` gives a root without `apt`; `docs/proposals/phase-b-image.md` and the research document assumed it would be there.
- Test A boots the older slot by hand with `BootNext`; that makes slot b the first entry in `BootOrder` (it confirms itself). The floor stays, but the **slot order** is now "older release first". A rule that a confirmed boot may not make an older release the preferred slot is not built (UNKNOWN whether it is wanted).

**Row click (test H3b, added in the phase B round after this one).** H3b first closes the AI Box window with `hubd end ai-1`, then opens the menu with the bar click and clicks the `ai-1  AI Box` row with the QEMU relative mouse, and checks that hubd opened that machine again: `driftwm msg state` shows `hubos-ai-1 [0, -100]`, the home position. How it was made reliable (all TESTED in this guest):
- **The pointer scale is measured first.** The test sends the pointer to the bottom right corner, moves it by (-150,-150) and finds the arrow in a screenshot (`findCursor`); it measured x 1.00, y 0.99 pixels per monitor unit, and divides the next moves by that. (An earlier try with one big jump from the bar item landed far from the row; the way that works is the one of the desktop experiment: send the pointer to the top-left corner, then one move to the row at (100,213).)
- **One click only selects the row; the second click opens the machine.** A single click left the menu open (`wofi` still running, no window); two clicks 300 ms apart opened the machine at its home (attempt 1 failed, attempt 2 succeeded in the dev run; the final runs use two clicks from the start). Whether that is wofi's normal behaviour or an effect of the virtual mouse is UNKNOWN. (libinput saw one press and one release for each click, `seat count` 1 then 0.)
- The pointer arrow is **not drawn while it is over the wofi list** (wofi sets no cursor image), so a screenshot cannot show where the pointer is; that is why the scale is measured on the empty canvas.
- **A bug found by this test, and fixed:** `follow-driftwm` found the compositor with `pidof driftwm`, which also lists a short-lived `driftwm msg ...` command (the test and any person typing `driftwm msg state` start one). When that command was the first pid listed, the script believed the compositor had been replaced, killed Waybar and hubd and let s6 start them again (the bar disappeared for about 20 s and the first menu click found no bar). It now picks the process whose command line has `--backend` (the compositor itself). Before the fix the menu opened only on the second try; after it, on the first.
- Not shown: a click on a row of a machine that is down, the keyboard path (Enter), a menu with more rows than fit the window (scrolling).
